# AI 对话评测系统 - 项目思考与演进历程

> 作为一名刚入行的 AI 产品经理，我在这个项目中遇到了什么问题、如何思考解决方案、以及对未来的规划

---

## 一、项目缘起：我遇到了什么问题

### 1.1 痛点发现

作为 AI 产品经理，我负责一个医美咨询场景的 AI 客服项目。上线后，我发现一个棘手的问题：

> **"AI 客服回复的质量参差不齐，但我无法系统性地评估和改进。"**

具体表现：
- 有些回复用户觉得很好，有些却投诉"答非所问"
- 运营同事反馈某些回复"太生硬"，但缺乏量化标准
- 我想改进 Prompt，但不知道具体哪里有问题

### 1.2 现有方案的局限

我调研了现有的评测方式，发现都不太理想：

| 方案 | 问题 |
|------|------|
| **人工质检** | 成本高、效率低、标准不统一，每天只能抽检几十条 |
| **规则匹配** | 只能检测关键词，无法理解语义，容易误判 |
| **传统 NLP** | 难以评估"共情"、"权威感"这类软性指标 |
| **用户反馈** | 滞后、样本偏差大，投诉的只是冰山一角 |

### 1.3 核心需求提炼

我梳理了自己的核心需求：

1. **自动化**：能批量评测对话日志，不依赖人工
2. **多维度**：不止"好/坏"，要细分维度（清晰度、共情度、准确性等）
3. **可追溯**：不止告诉我"哪里错了"，还要告诉我"为什么错"和"怎么改"
4. **效率高**：评测速度要快，Token 成本可控

## 二、解决思路：我是如何思考的

### 2.1 灵感来源：LLM-as-a-Judge

在阅读 AI 评测相关论文时，我了解到 **LLM-as-a-Judge** 这个范式：

> 用大语言模型作为评测裁判，对另一个 AI 的输出进行评分和分析。

这让我眼前一亮：
- LLM 能理解语义，不是简单的规则匹配
- LLM 能评估"软性"指标，比如语气、共情、权威感
- 通过 Prompt 定义评分标准，灵活可调

### 2.2 我的设计思路

#### 2.2.1 先确定评什么（评分维度）

我参考了客服质检的行业标准，结合医美咨询场景，定义了 6 个核心维度：

| 维度 | 为什么重要 |
|------|-----------|
| **表达清晰度** | 用户能否快速理解回复内容 |
| **主动引导能力** | AI 是否能挖掘用户需求，推进对话 |
| **内容价值呈现** | 是否传递了有用信息和产品优势 |
| **专业权威感** | 用户是否信任 AI 的专业能力 |
| **信息准确性** | 是否有事实错误或虚假承诺 |
| **语气共情度** | 是否让用户感到被理解和尊重 |

#### 2.2.2 再确定怎么评（评测流程）

我设计了两阶段评测流程：

**Phase 1：快速打分**
- 让 LLM 对每条 AI 回复按 6 个维度打 1-5 分
- 同时输出简短的综合分析

**Phase 2：深度分析（仅低分触发）**
- 低分回复单独进行根因分析
- 结合工作流配置，溯源到具体节点
- 给出可执行的 Prompt 修改建议

#### 2.2.3 最后解决效率问题

最初的设计是每个维度单独调用 LLM，导致：
- 一条回复需要 6 次 LLM 调用
- 评测速度慢，Token 消耗大

后来我优化为 **合并评测**：
- 一次调用同时输出 6 个维度的分数
- 效率提升 6 倍

### 2.3 关键设计决策

#### 决策 1：综合分如何计算？

**问题**：如果某个维度得 1 分（比如信息准确性有虚假承诺），但其他 5 个维度都是 5 分，平均分是 4.33——看起来"良好"，但实际上有严重问题。

**我的思考**：
- 单纯平均分会掩盖短板
- 某些维度的低分是"一票否决"的（比如虚假承诺）

**解决方案**：最低分惩罚机制
```
综合分 = min(平均分, 最低分 + 1.5)
```

这样，上面的例子综合分变成 2.5，会触发深度分析。

#### 决策 2：如何做到"全链路可观测" (v0.9.0)？

**问题**：随着系统支持 Agent 评测，仅仅记录分数已经不够，需要看到工具调用的过程和性能指标。

**我的思考**：
- Agent 的执行是多步的，不能只看结果
- 性能（Latency/Token）也是质量的一部分
- 需要一个统一的地方存储所有类型的 Traces

**解决方案**：引入 TraceStore 和统一调度器
- **eval_dispatcher**: 统一管理 Chat 和 Agent 的评测入口
- **TraceStore**: 仿 Langfuse 结构的本地存储，记录完整的输入输出和性能指标

## 三、功能实现：这个系统解决了什么

### 3.1 核心功能价值

| 功能 | 解决的问题 |
|------|-----------|
| **合并评测** | 效率提升 6 倍，Token 成本降低 80% |
| **综合分算法** | 不遗漏任何维度的严重问题 |
| **Trace 追踪** | Agent 思考链、耗时、Token 全透明 |
| **统一调度** | 单轮/多轮/Agent 一站式评测体验 |
| **可视化看板** | 组合图+散点图，直观发现质量瓶颈 |

## 四、迭代历程：项目是如何演进的

### v1.0：能跑起来
**目标**：验证 LLM-as-a-Judge 的可行性。
**成果**：简单的 CLI 脚本，逐维度打分。

### v2.0：能用了
**目标**：增加深度分析，支持问题诊断。
**成果**：两阶段评测，支持 Dify 工作流溯源。

### v3.0：好用了
**目标**：效率优化 + 评分精准 + 数据持久化。
**成果**：合并评测 (6x效率)，最低分惩罚，SQLite 存储。

### v0.9.0：全链路可观测 (当前版本)
**目标**：统一评测架构，支持 Agent，增强可视化。
**成果**：
- **Unified Dispatcher**: 统一调度器，自动路由评测类型。
- **Agent Eval**: 支持工具调用链评测。
- **Dashboard 2.0**: 引入 Plotly 交互图表 (Combo/Scatter/Heatmap)。
- **Trace System**: 完整的 Trace 记录与详情回放。

## 五、后续规划：还有哪些可以优化

### 5.1 短期优化（1-2 周）

#### 5.1.1 评测体系优化
- [ ] **维度权重可配置**：不同场景可能需要不同的权重，比如医美咨询更看重"信息准确性"
- [ ] **自定义维度**：除了预设的 6 个维度，支持用户添加业务特定的维度
- [ ] **检查清单细化**：每个维度的低分检查项需要更具体，便于 LLM 准确识别

#### 5.1.2 工程优化
- [ ] **并行评测**：多线程/异步调用，进一步提升速度 (v0.9.5)
- [ ] **API 服务化**：完善 Flask API，支持外部系统调用 (v1.0.0)

### 5.2 中期规划（1-2 个月）

#### 5.2.1 功能增强
- [x] **Agent 评测** (v0.9.0 已完成)
- [x] **Trace 存储** (v0.9.0 已完成)
- [ ] **评测对比**：对比不同批次的评测结果，验证 Prompt 优化效果
- [ ] **趋势分析**：时间维度的质量变化曲线 (Dashboard已初步支持)

### 5.3 长期愿景（3-6 个月）

#### 5.3.1 评测标准体系化
- 总结不同场景的评测标准模板
- 形成行业级的对话质量评测规范

#### 5.3.2 闭环优化
- 评测 → 分析 → 优化 → 验证的完整闭环
- 自动生成训练数据，用于模型微调

## 六、反思与收获

### 6.1 我学到了什么
1. **从用户痛点出发**：不是先想功能，而是先想"用户遇到了什么问题"
2. **架构演进**：从脚本到应用，再到统一调度平台，架构是随着需求复杂度自然演进的
3. **可观测性价值**：Trace 和 Metrics 不仅是给开发看的，也是产品优化质量的重要依据

### 6.2 还有哪些不足
1. **主观性**：LLM 评测仍存在偏好，未来可考虑引入"LLM 陪审团"机制
2. **性能**：大量数据评测时，串行处理较慢，需要异步并发支持
